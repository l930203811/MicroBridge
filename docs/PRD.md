# 微音桥 MicroBridge — 产品需求文档（PRD）

| 项 | 值 |
|---|---|
| 版本 | 0.1.0（M0 / M1 骨架） |
| 状态 | 需求已锁定，工程骨架已建立，M2 未开工 |
| 平台 | Windows x64（首发） |
| 技术栈 | C++20 + JUCE 8 |

## 1. 需求来源与锁定结论

来自 DeepSeek 完整分享对话（8 轮）中确定的约束：

1. 直播场景的**调音台 / 机架类**产品；
2. **只做调音台，不做混音编辑** —— 明确排除时间线、编辑历史、多轨剪辑；
3. 三个硬指标：**占用低、延迟低、界面美观**；
4. 命名：中文 ≤ 3 字、有个性、中英直译简单，含「微 / 声 / 音」字样。

用户后续追加的关键需求（改变了产品性质）：

> **不做总线，每条通道可输出到任意驱动设备，通道之间可互相发送信号。**

这条使产品从「调音台」变为**软件配线架 / 音频路由矩阵**：层级总线模型失效，
改为带增益的有向图。

本轮用户拍板：

- 命名 **微音桥 / MicroBridge**；
- **重新在 `D:\Xiangmu` 创建新项目**；
- **插件不要动、也先不做**（S-Rack 不动；新工程不托管 VST3），理由是插件体积太大，
  当前定位是**轻量化机架**；以后看情况再决定是否加入；
- 开发方向：**C 新建独立工程**（不改造 S-Rack）。

## 2. 一句话定位

> 一个 Windows 上的轻量音频路由机架：把麦克风、播放器、线路输入当成通道，
> 用一张可视化连线图决定「谁送给谁、谁输出到哪个设备」，不经过任何固定总线。

与 Voicemeeter 一类「虚拟混音台」的差异：后者靠 A/B 两条总线路由，
本产品**没有总线**，每条通道可同时、独立地送向多个设备。

## 3. 目标用户与场景

- 直播主：麦克风 + 伴奏 + 游戏/浏览器声音，分别送监听耳机、OBS、录音软件；
- 播客 / 远程会议：把不同应用音频分开路由到不同虚拟设备；
- 需要「一条通道同时喂多个输出」而不想装重型 DAW 的用户。

## 4. 范围边界

### 做

| 能力 | 说明 | 阶段 |
|---|---|---|
| 通道条 | 增益推子、静音 / 独奏、电平表、彩色分组 | **M1+ 已提前完成 UI**（声像留 M2） |
| 通道互送 `C→C` | 带 send 增益，post-fader | M1 内核 / M1+ UI |
| 通道直送设备 `C→D` | 带增益，一条通道可同时送多个设备 | M1 内核 / M1+ UI |
| 反馈环处理 | 建边时拓扑检测，成环直接拒绝并提示 | M1（内核已实现，UI 已提示） |
| 路由矩阵 UI | 通道条式插槽，可增删边与调增益 | **M1+ 已提前完成**（尚未接入音频线程） |
| 预设 | 路由矩阵保存 / 加载（JSON） | M4 |
| 双语 UI | 中 / EN 切换，默认中文 | **M1+ 已提前完成** |
| 原生效果 | 门、压缩、EQ（自实现，不托管插件） | M3 |

### 不做

时间线、多轨剪辑、编辑历史、离线导出、录音编辑、AI 人声分离 / 模型推理、
VST3 插件托管、虚拟声卡驱动随包安装、macOS / Linux（首发）。

### 依赖排除清单（轻量化硬约束）

ONNX Runtime、AI 模型文件、VST3 SDK、Media Foundation 解码器、
虚拟声卡驱动 `.sys`、Web 浏览器组件、CURL、MP3 解码。
JUCE 只引用不复制，构建产物目标为**单文件几 MB 级**，而非 S-Rack 的 70 MB 级发布包。

## 5. 核心模型

```
没有 Bus 节点。
两组边：edges = { C→C (send gain), C→D (gain) }
推子 fader[c] = 通道 c 所有出边的公共增益
静音 c = 断开 c 的全部出边
独奏集合 S = 只保留 src ∈ S 的出边
```

本质是一个 `(N×N + N×M)` 的**稀疏增益矩阵**。MVP 只编译非零边进处理计划，
零增益 / 静音 / 未连接边不进入实时计算。

## 6. 功能与验收硬指标

| 指标 | 目标 | 验收方式 |
|---|---|---|
| 缓冲区 | 64–128 samples @ 48 kHz 无爆音 | M1 空链路连续试听 30 分钟 |
| 延迟 | 端到端 ≤ 10 ms（单设备，含缓冲） | 环回测量 |
| CPU | 空闲 < 2%，满载路由 < 8%（4 核参考机） | 任务管理器 / 内部计数 |
| 安装包 | < 15 MB（不含外部虚拟声卡） | 打包后核验 |
| 多设备稳定性 | 双设备连续 30 分钟无漂移、无爆音 | M2 长跑 |
| 界面 | **浅色机架风格**（参照主流机架控制台）、双语无乱码、900×520 下无重叠 | 人工评审 + 窗口截图自查 |
| 反馈环 | 任何 `A→B→A` 连接被拒绝且图不被污染 | 单元测试（已覆盖） |
| 实时线程 | 零分配、零锁、零字符串、零文件 I/O | 代码审查 + 长跑 |

## 8. 已定技术决策（含理由）

| 决策 | 取值 | 理由 |
|---|---|---|
| 语言 / 框架 | C++20 + JUCE 8 | 本机无 Rust 工具链；已有跑通的 JUCE 8 工程链路；直播场景的虚拟设备生态是 C++ |
| JUCE 引入方式 | `JUCE_DIR` 只读引用 S-Rack 的 8.0.15 | 避免复制数百 MB，保持新工程轻量；可用 `-DJUCE_DIR` 覆盖 |
| 反馈环 | MVP **拒绝连接** | UI 提示直观、不引入延迟，守住低延迟指标；M3 再评估「回边加 1 block 延迟」 |
| 并发输出设备 | MVP 上限 2 个 | Windows 无原生聚合设备，每设备独立晶振；先降风险 |
| 互送增益 | 统一 post-fader | 简化语义，pre-fader 留到 M3 |
| 内部时钟 | 单一主时钟 + 每设备自适应环形缓冲 + 轻量 ASRC | 多设备 ppm 级漂移必然导致欠载爆音 |
| 虚拟音频输出 | 用户自备 VB-CABLE / Voicemeeter | 驱动签名、管理员权限、系统兼容是最大的坑，不压在首版 |
| VST3 插件链 | **本版不做，仅预留插入点** | 用户明确要求轻量化；插件托管会显著增大体积与依赖 |
| 与 S-Rack 关系 | 完全独立、不改动 | 用户明确「插件不要动」 |
| 命名 | 微音桥 / MicroBridge | 用户拍板；含「微/音」、3 字、中英直译简单 |

## 9. 风险与未决项

1. **多设备时钟漂移**（最高风险）：M2 的核心难点，需实测 30 分钟长跑；
   首版先限 2 个设备。
2. **命名撞车**：`MicroBridge` 在 GitHub 有 Arduino 时代同名项目，国内有公司字号含「音桥」；
   开源产品名可用，注册商标需做第 9/42 类近似查询。
3. **JUCE 8 Direct2D 渲染不稳定**：基线关闭 Direct2D 用软件渲染，电平表限帧约 30 fps。
4. **未决**：M3 是否重新评估 VST3 插件链（用户说「以后看情况再决定」）；
   M2 是否支持 WASAPI loopback 抓取应用音频；是否随包提供虚拟声卡驱动。
5. **M1 的路由 UI 尚未接入音频线程**：界面里的增删边 / 推子 / M·S 会实时更新
   `ProcessingPlan`，但 `AudioEngine` 仍是单设备直通，声音不会随矩阵变化。M2 补齐。
6. **JUCE 8 中文编码**：`String(const char*)` 按 ASCII 逐字节构造，裸传中文会乱码；
   已统一由 `I18n.h` 的 `S()` / `tr()` 用 `CharPointer_UTF8` 包装，新增文案必须走这一层。
